# Быстрые заявки и Telegram через SOCKS5h

В калькуляторе теперь достаточно Telegram/телефона и согласия. Имя не требуется. Поддерживаются @username, username, t.me/username, https://t.me/username и номера с кодом страны. Сумма, услуга, расчёт и рекламные метки прикладываются автоматически. Остальные формы тоже используют короткий вариант.

## На собственном сервере из архива

В `.env` в папке `site/` задайте:

```
TELEGRAM_BOT_TOKEN=<токен вашего бота>
TELEGRAM_CHAT_ID=<ID вашей группы>
TELEGRAM_PROXY_URL=socks5h://<логин>:<пароль>@<хост>:<порт>
```

Прокси без авторизации: `socks5h://<хост>:<порт>`. Спецсимволы логина и пароля кодируйте как части URL, например @ → %40 и : → %3A. После изменения перезапустите сервер. Боту нужны права отправлять сообщения в целевую группу.

Маршрут всегда проходит через SOCKS5h, включая разрешение имени api.telegram.org. TLS проверяет сертификат Telegram. Автоматического перехода на прямое соединение нет. Прокси вида http:// или socks5:// отклоняются.

Заявка сначала сохраняется на сервере, затем синхронно отправляется в Telegram. Полученный message_id записывается в журнал доставки. При штатном повторе запроса с тем же requestId уже доставленная заявка повторно не отправляется. При недоступности прокси/Telegram остаётся статус pending и можно повторить отправку с тем же номером.

В интерфейсе «отправлено в Telegram» появляется только после подтверждения Bot API. При сбое portable-сервер сохраняет заявку со статусом pending, но возвращает HTTP 503: посетитель может повторить отправку. Автоматической фоновой доставки нет. Telegram Bot API не предоставляет собственного ключа идемпотентности: журнал защищает от повторных кликов и обычных повторов, но авария процесса между внешней доставкой и записью подтверждения теоретически может привести к повтору.

## Диагностика на VPS

Нужны системный `curl` в PATH службы и актуальные корневые сертификаты. В Ubuntu: `apt install -y curl ca-certificates`.

Для конфигурации из `docs/DEPLOY-VPS.md` выполните:

```bash
cd /opt/clever/site
node --env-file=/etc/clever/clever.env server.mjs --check-telegram
```

При локальном запуске из `site/`: `node --env-file=.env server.mjs --check-telegram`.

Проверка выполняет `getMe`, `getChat` и для группы/канала `getChatMember` по тому же SOCKS5h-маршруту. Она не отправляет сообщений, не запускает HTTP-сервер и не записывает заявки. Успех даёт код выхода 0; ошибка — 1, безопасный код и подсказку. В личном чате проверяется доступ к чату; фактическую отправку подтверждает только тестовая заявка.

| Код | Что проверить |
|---|---|
| `not_configured` | Env-файл загружен, токен и числовой Chat ID заполнены |
| `proxy_invalid` | Формат `socks5h://[логин:пароль@]хост:порт` |
| `ENOENT` | `curl` доступен в PATH службы |
| `curl_5`, `curl_7` | DNS/адрес/порт прокси, firewall VPS |
| `curl_28` | Прокси не отвечает в отведённое время |
| `curl_60`, `curl_77` | Корневые сертификаты, системное время, путь/права CA-файла |
| `curl_67`, `curl_97` | Авторизация SOCKS, URL-кодирование пароля, IP allowlist, доступ прокси к Telegram:443 |
| `401`, `404` | Токен бота |
| `400`, `403`, `send_forbidden` | Chat ID, бот добавлен в чат, права отправки; в канале нужны права публикации |
| `429` | Лимит Telegram; подождите перед повтором |

Если используется свой PEM-файл CA, задайте `CURL_CA_BUNDLE=/полный/путь/ca.pem` (либо `SSL_CERT_FILE`). Сервер явно передаёт этот путь curl, в том числе на Windows. Без отдельного файла используется системное хранилище curl. Проверка TLS не отключается. `NO_PROXY` не обходит заданный SOCKS5h.

После обновления `site/server.mjs` и конфигурации: `systemctl restart clever`. Логи: `journalctl -u clever -n 50 --no-pager`. Не публикуйте содержимое env-файла. Диагностика не подтверждает доставку реального сообщения: после её успеха отправьте тестовую заявку через форму.

## Версия Cloudflare

`source/app/api/requests/route.ts` использует отдельный HTTPS-ретранслятор, а не локальный curl. В `site/server.mjs` маршрута `/api/telegram-relay` нет. Для готового VPS-сайта запускайте portable-сервер; настройка `TELEGRAM_PROXY_URL` в Worker сама по себе доставку не включает. Подключение ретранслятора — отдельная задача.

## Аналитика

`lead_success` означает подтверждённое сохранение обращения. Дополнительная цель `telegram_delivered` означает подтверждённую доставку уведомления. pending не считается доставкой в Telegram. Контакт и текст заявки в Метрику не передаются.

## Проверка кода

`node portable/run-telegram-test.mjs` из исходников проверяет авторизацию SOCKS, передачу доменного имени прокси, HTTPS с проверкой сертификата, формат сообщения, повторную доставку и поведение при ошибке. Используются локальные фикстуры; реальные Telegram-сообщения тест не отправляет.
